هدف این تمرین قرار دادن یک Reverse Proxy جلوی سرویس قدیمی go-httpbin است؛ به‌طوری‌که کاربران فقط از مسیر پراکسی به سرویس دسترسی داشته باشند و پراکسی پیش از ارسال هر درخواست، JWT را بررسی کند.

در این پیاده‌سازی از Envoy به‌عنوان Reverse Proxy و از ایمیج ghcr.io/mccutchen/go-httpbin به‌عنوان سرویس Legacy استفاده شده است.

معماری پیاده‌سازی

```text
Client
  |
  | HTTP :80
  v
Envoy JWT Reverse Proxy
  |  1. خواندن Authorization: Bearer <JWT>
  |  2. بررسی امضا، issuer، audience و زمان اعتبار
  |  3. رد درخواست نامعتبر با 401
  |
  | فقط پس از اعتبارسنجی موفق
  v
Private Docker Network
  |
  v
go-httpbin :8081
```

پورت ۸۰ میزبان فقط به کانتینر Envoy متصل است. سرویس go-httpbin هیچ پورت منتشرشده‌ای روی میزبان ندارد و فقط در شبکه داخلی Docker با Envoy ارتباط می‌گیرد.

**۱. چگونه می‌توان یک سرویس را فقط روی شبکه داخلی اجرا کرد؟**

برای داخلی نگه‌داشتن یک سرویس، باید دسترسی مستقیم شبکه‌های خارجی به آن را قطع کرد و فقط به میزبان‌ها یا اجزای مورداعتماد شبکه داخلی اجازه اتصال داد.

چند اقدام اصلی برای این کار وجود دارد:

1. سرویس روی یک IP خصوصی یا یک شبکه خصوصی اجرا شود و برای آن Public IP یا Port Forwarding مستقیم از اینترنت تعریف نشود.
2. با Firewall، Security Group یا ACL فقط مبدأهای مورداعتماد اجازه دسترسی به پورت سرویس را داشته باشند.
3. پورت سرویس Legacy روی اینترنت Publish نشود. فقط پورت Reverse Proxy در معرض شبکه بیرونی قرار بگیرد.
4. Reverse Proxy و سرویس Legacy در شبکه‌ای قرار بگیرند که ارتباط مستقیم کاربران اینترنت با آن ممکن نباشد.
5. دسترسی مدیریتی و مانیتورینگ سرویس نیز محدود شود و فقط از شبکه یا میزبان‌های مورداعتماد انجام بگیرد.

در این پروژه، Docker Compose دو شبکه ایجاد می‌کند. کانتینر jwt-proxy به شبکه ورودی edge و شبکه داخلی backend متصل است؛ اما کانتینر legacy-service فقط در شبکه backend قرار دارد. تنها پورت منتشرشده روی میزبان، پورت ۸۰ مربوط به Envoy است. بنابراین کاربر بیرونی نمی‌تواند مستقیماً به پورت ۸۰۸۱ سرویس Legacy متصل شود.

نکته مهم این است که خصوصی بودن شبکه به‌تنهایی جایگزین احراز هویت و کنترل دسترسی نیست؛ محدودسازی شبکه باید همراه با کنترل دسترسی مناسب انجام شود.

**۲. فلسفه TLS Termination چیست؟**

اTLS Termination یعنی ارتباط HTTPS ورودی در نقطه‌ای مانند Reverse Proxy خاتمه پیدا کند. در این روش، کلاینت با استفاده از HTTPS به Proxy وصل می‌شود. Proxy گواهی دیجیتال و کلید خصوصی مربوط به دامنه را در اختیار دارد، فرایند TLS Handshake را انجام می‌دهد و پس از برقراری ارتباط امن، داده‌های دریافتی را رمزگشایی می‌کند.

پس از آن، Proxy درخواست را به سرویس داخلی ارسال می‌کند. این ارتباط داخلی می‌تواند HTTP باشد یا برای امنیت بیشتر، دوباره با TLS رمزنگاری شود.

مزیت اصلی این روش آن است که لازم نیست سرویس قدیمی مستقیماً درگیر مدیریت گواهی، کلید خصوصی، تمدید گواهی و تنظیمات TLS شود. مدیریت TLS در یک نقطه متمرکز، یعنی Reverse Proxy، انجام می‌شود. همچنین می‌توان سیاست‌هایی مانند نسخه‌های مجاز TLS، Cipher Suiteها و گواهی‌ها را در همان نقطه مدیریت کرد.

با این حال، TLS Termination به معنی احراز هویت کاربر برنامه نیست. TLS از محرمانگی و صحت داده‌ها در مسیر ارتباطی محافظت می‌کند، اما JWT برای احراز هویت و کنترل دسترسی درخواست در سطح برنامه استفاده می‌شود. اگر شبکه داخلی قابل اعتماد نباشد یا داده‌ها حساس باشند، بهتر است ارتباط بین Proxy و سرویس Legacy نیز با TLS رمزنگاری شود. به این حالت معمولاً Re-encryption یا TLS از Proxy تا Backend گفته می‌شود.

**۳. پیاده‌سازی JWT Authentication Proxy**

اجزای استفاده‌شده:

- Envoy Proxy: دریافت درخواست‌های ورودی، بررسی JWT و ارسال درخواست معتبر به سرویس مقصد.
- go-httpbin: سرویس Legacy مورد استفاده در تمرین.
- Docker Compose: اجرای سرویس‌ها و ایجاد شبکه‌های جداگانه.
- JWKS: نگهداری کلید عمومی‌ای که Envoy برای بررسی امضای JWT استفاده می‌کند.

اEnvoy فیلتر داخلی envoy.filters.http.jwt_authn دارد. این فیلتر می‌تواند امضای JWT، صادرکننده توکن (iss)، مخاطب توکن (aud) و محدودیت زمانی توکن مانند exp را بررسی کند.

پیش‌نیازها:

- Docker Desktop با Docker Compose
- Python 3
- دسترسی اینترنت برای دریافت Docker Imageها

راه‌اندازی در Windows PowerShell:

ابتدا وابستگی پایتون را نصب کنید:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

سپس کلید آزمایشی، فایل JWKS و JWT را تولید کنید:

```powershell
python .\scripts\setup_dev.py
```

این اسکریپت یک کلید خصوصی RSA و یک کلید عمومی تولید می‌کند. کلید عمومی در فایل envoy/jwks.json قرار می‌گیرد و Envoy از آن برای اعتبارسنجی امضای JWT استفاده می‌کند. توکن آزمایشی نیز در فایل token.txt ذخیره می‌شود.

کلید خصوصی و توکن آزمایشی نباید به مخزن Git اضافه شوند؛ این فایل‌ها در .gitignore قرار گرفته‌اند. این روش صرفاً برای آزمایش محلی است و جایگزین Identity Provider واقعی در محیط عملیاتی نیست.

اکنون سرویس‌ها را اجرا کنید:

```powershell
docker compose up -d
```

وضعیت کانتینرها را بررسی کنید:

```powershell
docker compose ps
```

اگر پورت ۸۰ روی ویندوز قبلاً توسط برنامه‌ای مثل IIS اشغال شده باشد، نگاشت پورت در فایل docker-compose.yml را موقتاً از 80:8080 به 8080:8080 تغییر دهید و آدرس‌های آزمایش را از http://localhost/ به http://localhost:8080/ تغییر دهید. برای تطبیق نهایی با صورت تمرین، نگاشت را دوباره به 80:8080 برگردانید.

آزمایش عملکرد:

درخواست بدون JWT باید با پاسخ 401 Unauthorized رد شود:

```powershell
curl.exe -i http://localhost/headers
```

درخواست با توکن نامعتبر نیز باید 401 Unauthorized دریافت کند:

```powershell
curl.exe -i -H "Authorization: Bearer invalid-token" http://localhost/headers
```

برای ارسال درخواست با توکن معتبر:

```powershell
$token = (Get-Content .\token.txt -Raw).Trim()
curl.exe -i -H "Authorization: Bearer $token" http://localhost/headers
```

درخواست معتبر باید به سرویس go-httpbin برسد و پاسخ 200 OK دریافت کند.

برای اجرای همه آزمایش‌ها به‌ترتیب می‌توان از اسکریپت زیر استفاده کرد:

```powershell
.\scripts\test.ps1
```

برای بررسی معتبر بودن ساختار پیکربندی Envoy پیش از اجرا:

```powershell
docker compose run --rm --no-deps --entrypoint envoy jwt-proxy --mode validate -c /etc/envoy/envoy.yaml
```

برای مشاهده لاگ‌ها:

```powershell
docker compose logs -f jwt-proxy
docker compose logs -f legacy-service
```

برای متوقف‌کردن و حذف کانتینرها و شبکه‌های ساخته‌شده:

```powershell
docker compose down
```

نکات امنیتی این نمونه:

- فقط پورت ۸۰ روی میزبان Publish شده است.
- پورت ۸۰۸۱ فقط در شبکه داخلی Docker قابل دسترسی است و به میزبان Publish نشده است.
- Envoy برای تمام مسیرها وجود JWT معتبر را الزامی کرده است.
- کلید عمومی از فایل JWKS خوانده می‌شود و امضای JWT با الگوریتم RS256 بررسی می‌شود.
- مقدارهای iss و aud و زمان انقضای JWT بررسی می‌شوند.
- توکن پس از اعتبارسنجی به سرویس Legacy Forward نمی‌شود.
- کلید خصوصی فقط برای تولید توکن آزمایشی محلی است و نباید Commit شود.

این پیاده‌سازی برای نمایش مفاهیم تمرین و اجرای محلی است. برای محیط واقعی باید از Identity Provider معتبر، مدیریت امن کلیدها، HTTPS در ورودی، محدودیت نرخ درخواست، ثبت رویدادهای امنیتی و سیاست‌های مناسب شبکه استفاده شود.
